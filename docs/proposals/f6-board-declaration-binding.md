# F6: Bind Agency attestations to an immutable board declaration

- Status: PROPOSAL (design only, no code in this change)
- Tracking: repo issue #5 ("Bind Agency opt-in/evidence attestations to an immutable board declaration")
- Known limitation source: `integrations/agency-agents/README.md`, Safety model section ("KNOWN LIMITATION: none of these attestations is bound to a digest of the exact board declaration...")
- Code grounding: `scripts/lib/agency-orchestration.js` (`authenticatedControllerSnapshot`, `isPlainDataAttestation`, `isDeeplyPlainData`, `isPipelineOptInAttestation`, the evidence index inside `validateBoard`), `integrations/agency-agents/contracts.json`

## 1. Problem statement

An enabled Agency board is authorized by an authenticated `agency.pipeline-opt-in.v1` attestation that binds exactly two identifiers: `pipelineId` and `decisionId` (`isPipelineOptInAttestation`). Completed work is proven by authenticated `agency.card-evidence.v1` attestations that bind `pipelineId`, `cardId`, `evidenceId`, and `evidenceSha256` (the evidence index in `validateBoard`). Nothing in either kind commits to the content of the board the controller actually approved. The pipeline id is the only join key between the controller's decision and the declaration being validated.

Consequence (F6, issue #5): a controller that approves pipeline id `P` is trusted for whatever board later carries id `P`. A rewritten board — different roles, different budgets, different dependency graph, different stop conditions — validates under the original opt-in as long as it reuses the id, and evidence minted against the original board is indistinguishable from evidence for the rewrite. The fix is to bind a cryptographic digest of the exact approved board declaration into the attestations, so that approval and evidence are for one specific declaration and no other. The README's Safety model section records this as the one open known limitation of the current model; this proposal is the "future dedicated change" it defers to.

## 2. Why the previous attempt failed

An earlier revision of PR #4 shipped `computeBoardDeclarationDigest`. It produced a new P1 finding in six consecutive review rounds before it was removed outright (the comment above `isDeeplyPlainData` still notes it replaces a bound "the removed digest encoder used to provide"). Every failure was the same shape: the serialization was not injective over the real input domain, so two distinct boards could produce one digest, which converts the digest from a binding into a false sense of one. The concrete collision classes found in review:

1. **`__proto__` as a prototype-setter.** Re-serialization that rebuilt objects (object literals / property assignment) treated an own key named `__proto__` as a prototype set, silently dropping it. A board with an own `__proto__` property collided with the same board without it.
2. **Non-finite numbers under `JSON.stringify`.** `Infinity`, `-Infinity`, and `NaN` serialize as `null`, colliding with a literal `null` at the same position.
3. **Lone UTF-16 surrogates at encode time.** UTF-8 encoding replaces an unpaired surrogate with U+FFFD, so distinct strings (`"\uD800"` vs `"�"`, or any two distinct lone surrogates) collided.
4. **UTF-8 round-trip lossiness on the decode side.** `Buffer.from(str, 'utf8')` / `toString('utf8')` is not the identity on all JS strings, so any decode/re-encode step could map distinct inputs to one byte sequence.

A fifth class, accessor/Proxy TOCTOU (hash one value, hand the host another on a live re-read), is now closed at the boundary by the plain-data gate and is a precondition this design relies on rather than a problem it must solve.

These are design constraints, stated plainly: **the binding must be provably injective over exactly the input domain the validator accepts, and every "normalize then hash" step is a place where injectivity dies.** The previous attempt failed because it normalized (JSON re-serialization, UTF-8 transcoding) instead of either encoding losslessly or rejecting. This is why F6 needs a design with an explicit domain definition and injectivity argument, not another patch.

## 3. Requirements

- **R1 — Injectivity over the accepted domain, modulo the declaration projection and object-prototype identity.** Let `Project(x)` be the Section 5.1 declaration projection (the board with the volatile denylist fields removed). For any two boards `a`, `b` that pass the plain-data gate (`isDeeplyPlainData`) and fall inside the canonical domain (R4), the digest is injective over the **projected, prototype-blind** domain: `digest(a) === digest(b)` iff `Project(a)` and `Project(b)` are deeply equal under SameValue semantics on leaves (so `-0` and `+0` are distinct values; `NaN` never appears, see R4) **and under a content-only equality that ignores object prototype identity**. This means: two boards that differ only in volatile fields (e.g. a card's `status`) intentionally share a digest — that is the projection working, not a collision. Likewise, two boards identical in every declared key/value but differing only in whether some object node has `Object.prototype` or a null prototype (`Object.create(null)` — `isDeeplyPlainData` accepts both; see `scripts/lib/agency-orchestration.js`'s `prototype !== Object.prototype && prototype !== null` check) also intentionally share a digest: the encoding (5.2, 5.5) captures declared key/value content only, never internal object metadata, so prototype identity was never part of what gets hashed in the first place. This is a second, narrower quotient alongside the projection, not a new gap — it is invisible for every board that originates from `JSON.parse` (the only source `agency-doctor` ever produces, since JSON can never produce a null-prototype object) and only becomes observable for an in-process caller that hand-constructs one, an acceptance `isDeeplyPlainData` already makes for reasons outside this proposal's scope. Because R1's equality notion is explicitly content-only, the test harness (R6, Section 7.2) must use a matching content-only equality oracle, not a strict deep-equal (e.g. Node's `assert.deepStrictEqual`) that treats prototype as significant — such an oracle would misreport this intentional quotient as a collision. Modulo SHA-256 collision resistance.
- **R2 — Determinism across Node versions and platforms.** Same board, same bytes, same digest on any supported Node major, any OS, any endianness. No dependence on property-enumeration quirks, ICU, locale, or `JSON.stringify` implementation details.
- **R3 — Bounded cost.** The encoder reuses the existing caps (`MAX_BOARD_NODES` = 50000, `MAX_BOARD_DEPTH` = 64, `MAX_BOARD_PROPERTIES` = 100000) and runs only on boards `isDeeplyPlainData` has already accepted. It is iterative (explicit stack, like `isDeeplyPlainData`), never recursive, and cannot throw on shape — it fails closed with an error result. These caps bound tree shape (node count, depth, property count) but not individual string length, and `MAX_JSON_BYTES` bounds only boards read through the CLI's JSON parse — an in-process caller can hand `validateBoard` an object carrying one very large string directly. R3 therefore also requires a new aggregate cap, `MAX_ENCODED_STRING_UNITS = 1048576` (1024 × 1024, matching `MAX_JSON_BYTES`'s numeric ceiling as a code-unit count rather than a byte count — deliberately generous headroom, since an in-process caller isn't bounded by JSON-text size at all), on the total UTF-16 code units summed across every string in the tree — **including strings inside the volatile fields that projection will later drop** (5.1's complete-board R4 pass runs before projection, so an oversized string hidden in `evidence` or another excluded field is not exempt). Checked incrementally as the walk proceeds, so the encoder fails before allocating the oversized payload (see 5.4).
- **R3a — Array own-properties are fully covered or rejected.** The plain-data gate must reject any array carrying an own enumerable string-keyed property outside its dense indices and `length` (e.g. `arr.approval = 'x'`); the array encoding (5.2) has no slot for such a property, so silently accepting it would let it change without changing the digest.
- **R3b — Non-enumerable own properties are fully covered or rejected, except an array's intrinsic `length`.** The plain-data gate must reject any **non-array** object carrying a non-enumerable own property; `Object.keys` (5.5) cannot see it, so an accepted-but-invisible field would likewise be able to change without changing the digest. Arrays are exempted from this rule for `length` specifically — `length` is non-enumerable by ECMAScript specification on every array, so a blanket non-enumerable-property ban would reject every array outright, contradicting R3a and the `0x05` encoding, which both require arrays to be representable. Arrays remain fully covered by R3a's exact-index check (below), which is a stricter and more specific rule than R3b for the array case.
- **R3c — Inherited enumerable properties are rejected.** The plain-data gate must reject any node in the board tree that exposes an *inherited* enumerable property, i.e. any node for which `for...in` yields a key that `Object.hasOwn` does not confirm. The gate, the R4 domain pass and the encoder all read OWN keys only (`Reflect.ownKeys`/`Object.keys`), while `validateBoard` and the host read individual fields through ordinary property access (`card.stopCondition`, `budget.turns`), which walks the prototype chain. In a prototype-polluted process — `Object.prototype.stopCondition = '...'`, reachable from a data-driven merge/clone gadget over attacker JSON elsewhere in the host, a well-known Node vulnerability class — a card merely *missing* that key as an own property is encoded without it while validation still consumes the inherited value. Two entirely different effective declarations then share one digest, which is precisely the binding this proposal exists to provide. This is the same own-property rule R3a already applies to array indices (`Object.hasOwn`, not `in`, so an inherited numeric property cannot pass a hole off as filled), generalised to every key of every node. It does **not** weaken R1's deliberate prototype-blind quotient: R1 says two nodes with identical *content* digest alike whether their prototype is `Object.prototype` or `null`, which holds only because a pristine prototype contributes no content — R3c is what makes that premise true rather than assumed. Residual, stated rather than left implied: an inherited **non-enumerable** property (`Object.defineProperty` against an intrinsic prototype) is invisible to `for...in` and is not caught; unlike assignment-based pollution it is not reachable through a data-driven gadget, only by arbitrary in-process code execution, at which point no gate in the file means anything.
- **R4 — Fail closed outside the canonical domain.** Any value the canonical encoding cannot represent injectively is **rejected**, never normalized: non-finite numbers (`Infinity`, `-Infinity`, `NaN`) are a hard validation error; values of type `undefined`, `bigint`, or anything else non-JSON-shaped are a hard error. Lone surrogates ARE inside the domain (a JSON parser produces them from `"\uD800"` escapes, and in-process callers can hand any JS string) and are encoded losslessly. Normalization is what caused every historical collision; rejection or lossless encoding are the only two allowed moves.
- **R5 — Verifier compatibility.** The digest travels inside the existing authenticated attestation snapshot (`authenticatedControllerSnapshot`: shallow `Object.freeze({...attestation})`, top-level scalar fields only) as a new versioned field or kind. No weakening of the frozen-snapshot model: no nested objects in attestations (the freeze is shallow and `isPlainDataAttestation` inspects only top-level descriptors), predicates keep reading bound fields from the snapshot only.
- **R6 — Testable injectivity.** Dedicated regression pairs for each historical collision class, plus property-based/fuzz evidence (random board pairs from a domain generator: digests equal iff deeply equal) before the digest is trusted for anything. The digest earns trust from test evidence, not from code review alone — six review rounds already demonstrated review alone is insufficient here.
- **R7 — A malformed binding field must never be invisible to the predicates.** `authenticatedControllerSnapshot`'s shallow `Object.freeze({...attestation})` spread copies only *enumerable* own properties, but `isPlainDataAttestation` (the attestation-shape gate) currently rejects accessors and Proxies without checking enumerability at all — it accepts a non-enumerable own data property as valid plain data. Left as-is, a non-enumerable `boardBindingKind` or `boardDigest` — however malformed or wrong — would silently vanish from the snapshot the predicates actually read, becoming indistinguishable from "absent" and directly violating Section 6's disposition-matrix rule that malformed values must never collapse into absent (a malformed field would instead warn-accept under Phase 1, exactly the failure mode that rule exists to prevent). `isPlainDataAttestation` must therefore also reject any non-enumerable own property. Unlike R3b, there is no array exemption to carve out here: attestations are always plain, non-array objects (`isPlainAttestationObject` already excludes arrays before calling `isPlainDataAttestation`), so this can be a flat rejection with no `length`-style special case.

## 4. Candidate approaches

### 4a. RFC 8785 JCS (JSON Canonicalization Scheme)

Canonical JSON text: keys sorted by UTF-16 code units, numbers in ECMAScript shortest-round-trip form, minimal string escaping; SHA-256 over the UTF-8 bytes.

- **Pros.** Published, reviewed spec (R2 strong); human-readable canonical form aids debugging; interop if a non-JS verifier ever appears; number serialization is exactly ECMAScript `Number::toString`, available natively.
- **Cons.** JCS **requires** well-formed Unicode and finite numbers: lone surrogates and `Infinity`/`NaN` are simply outside its domain. Used naively it re-imports collision classes 2 and 3 (that is roughly what the failed attempt was). Sound use therefore means a strict pre-pass that rejects lone surrogates and non-finite numbers first — which aligns with R4 for numbers, but for strings it shrinks the accepted domain: boards that `JSON.parse` happily produces (lone-surrogate escapes) would start failing validation, a behavior change beyond adding a digest. It also loses `-0` (JCS serializes `-0` as `0`), a silent SameValue collision unless `-0` is also rejected. And there is no vetted zero-dependency JCS implementation in the repo; hand-writing shortest-round-trip serialization plus the escaping rules is its own bespoke-crypto-adjacent surface, with a text indirection (string → UTF-8) where class-3/4 bugs historically lived.
- **Verdict.** Sound only as "JCS with strict rejection of lone surrogates, non-finite numbers, and `-0`". Injective on the reduced domain, but the reduction is a real functionality cut and the implementation burden is not smaller than a custom binary encoding.

### 4b. RFC 8949 CBOR Core Deterministic Encoding

Deterministic CBOR: definite lengths, shortest integer encodings, bytewise-sorted map keys; SHA-256 over the CBOR bytes.

- **Pros.** Published deterministic-encoding profile (R2 strong); binary, so no escaping layer; maps/arrays/floats all covered; widely analyzed.
- **Cons.** The repo has zero runtime dependencies and vendoring a CBOR library contradicts that; a bounded self-written subset is possible but then the "vetted encoder" advantage evaporates — it is bespoke code wearing a standard's name, and reviewers must check it against RFC 8949's deterministic rules (preferred serialization, shortest-float rules) as well as against R1. CBOR text strings require valid UTF-8, so lone surrogates again force either rejection or a switch to byte strings carrying UTF-16 — at which point the encoding is no longer plain CBOR interop anyway. NaN payload/shortest-float subtleties add rules we do not need since R4 rejects non-finite values.
- **Verdict.** Workable, but in this repo it degenerates into the custom encoder of 4c with extra spec-conformance obligations and no realized interop benefit.

### 4c. Custom length-prefixed, type-tagged byte encoding (recommended)

Every node is emitted as: 1-byte type tag, big-endian length/count where variable, raw payload bytes. Strings are length-prefixed sequences of UTF-16 **code units** (2 bytes each, big-endian), so lone surrogates are represented losslessly with no transcoding step. Object keys sorted bytewise over their encoded form. SHA-256 over the concatenated stream.

- **Pros.** Injective **by construction** over exactly the accepted domain, with a short structural-induction proof (Section 5); no Unicode transcoding anywhere, so classes 3 and 4 are impossible rather than guarded against; no re-materialization of objects, so class 1 is impossible (keys are only ever bytes); class 2 handled by R4 rejection; zero dependencies; the domain is defined by us to match what `validateBoard` actually accepts, instead of shrinking our domain to fit a spec's.
- **Cons.** Bespoke crypto-adjacent code with no external spec to lean on — the spec below plus the R6 test evidence must carry the entire trust burden; no interop with non-JS verifiers without porting the spec; a canonical byte stream that humans cannot eyeball (mitigate: a debug pretty-printer for tests only, never on the digest path).
- **Verdict.** Best fit. The failure history shows the danger is normalization and transcoding layers, and this is the only candidate with none of either.

## 5. Recommendation

Adopt **4c**: a custom length-prefixed, type-tagged encoding with strict rejection of non-finite numbers, digested with SHA-256. Specification, precise enough to implement:

### 5.1 What is digested: the declaration projection

The digest covers the **board declaration**, not live execution state. Otherwise every status transition would invalidate the opt-in and force a fresh controller decision per move. Projection rule, fail-closed by construction (a **denylist** of volatile fields, so any unknown or future field is covered by default — an allowlist would let a rewrite hide in an unlisted field):

- Start from the exact board object that passed `isDeeplyPlainData`.
- **R4 validation runs over the complete board, before projection, not over the projected value.** The volatile fields (`board.enabled`, `board.correctionCycles`, per-card `status`/`attempts`/`evidence`) are dropped from the *encoding*, but they are not exempt from the canonical-domain check: a non-`done` card carrying `evidence: [Infinity]`, for instance, must still fail R4's hard validation error even though `evidence` never reaches the encoder. Narrowing R4 to only the projected value would let a non-finite number, `undefined`, or any other R4-rejected shape hide inside a to-be-skipped field and silently pass. This same full-board pass is also where the aggregate string-size cap (R3, `MAX_ENCODED_STRING_UNITS`, 5.4) accumulates its running total, for the identical reason: a string inside `evidence` or another volatile field must count toward the cap even though it will never reach the encoder. The check order is therefore: (1) `isDeeplyPlainData` gate, (2) R4 canonical-domain validation over the whole board including volatile fields, accumulating the R3 string-size total as it walks, (3) projection and encoding of the surviving (non-volatile) fields.
- Drop exactly these fields, nothing else: `board.enabled`, `board.correctionCycles`; and per card: `status`, `attempts`, `evidence`.
- Everything else is covered, including `schemaVersion`, `pipelineId`, `depth`, `pipelineMinutes`, and per card `id`, `title`, `role`, `mode`, `canSpawn`, `stopCondition`, `dependencies` (in declared order), the full `budget` object, and **any field not named in the drop list**.
- Card array order is part of the declaration. No sorting of cards, no sorting of dependency arrays: reordering is a rewrite. The only sorting anywhere is object-key ordering (5.5), which removes an artifact of JS enumeration order, not declared structure.
- The projection is computed structurally during encoding (skip the named keys at the named positions); the board object is never copied or rebuilt, so no re-materialization step exists for class 1 to hide in.

### 5.2 Type tags

One byte per node, first byte of every node's encoding:

| Tag | Type | Payload |
|-----|------|---------|
| `0x00` | null | none |
| `0x01` | false | none |
| `0x02` | true | none |
| `0x03` | number (finite only) | 8 bytes: IEEE-754 binary64 bit pattern, big-endian |
| `0x04` | string | 4-byte big-endian code-unit count `n`, then `n` × 2-byte big-endian UTF-16 code units |
| `0x05` | array | 4-byte big-endian element count `n`, then the `n` encoded elements in order |
| `0x06` | object | 4-byte big-endian entry count `n`, then `n` entries, each = encoded key (a `0x04` string node) followed by encoded value, entries sorted per 5.5 |

Any value of any other type (`undefined`, `bigint`, `symbol`, function — the last two already excluded by the plain-data gate) is a hard error: the digest computation fails and `validateBoard` reports a board error. There is no "unknown" tag on purpose.

**Array own-properties (R3a).** The `0x05` array encoding records only `length` and the `n` indexed elements. A JS array can carry additional own string-keyed properties outside its dense indices (e.g. `board.cards.approval = "decision-1"`), and those would have no representation in the encoding — silently making the digest blind to them. `isDeeplyPlainData` must therefore reject (not silently drop) any array whose own keys are not exactly its dense indices plus `length`.

A bare cardinality check (`Reflect.ownKeys(value).length === value.length + 1`) is **not sufficient**: it does not prove the keys present are *exactly* `0` through `length - 1` plus `length` — a missing index (a hole) and an unrelated extra own property can cancel out and preserve the expected count while both defects are present simultaneously. The existing `isDeeplyPlainData` array loop also uses `i in value`, which is true for an *inherited* numeric property (e.g. via a polluted prototype already rejected elsewhere in the gate, but worth naming explicitly here since this check must not regress that guarantee) and would therefore treat a hole as filled when it is not truly an own property. The correct check: for every `i` from `0` to `length - 1`, require `Object.hasOwn(value, String(i))` (own, not inherited); and require that `Reflect.ownKeys(value)` contains no keys other than those `length` indices plus `"length"` itself (rejecting symbol keys too, though those are already excluded elsewhere in the gate). This closes the gate, not just the encoder, since the encoder only ever sees what the gate already accepted.

### 5.3 Numbers

- **Reject non-finite.** `Infinity`, `-Infinity`, and `NaN` fail the digest with a validation error. They are not JSON, `JSON.parse` cannot produce them, and normalizing them to anything is collision class 2. In-process callers who hand them in get a rejection, not a digest. This also puts all NaN bit-pattern/payload variability out of scope by rejection — no canonical-NaN rule is needed because no NaN is ever encoded.
- **Encode the exact bit pattern.** Finite numbers are encoded as the 8-byte big-endian IEEE-754 binary64 bit pattern (`DataView.setFloat64(offset, v, false)`). Explicit rule for zero: `-0` and `+0` have distinct bit patterns (`0x8000000000000000` vs `0x0000000000000000`) and therefore **distinct digests** — SameValue semantics, per R1. `JSON.parse('-0')` produces `-0`; treating it as equal to `0` would be a normalization, and normalization is banned. Each finite double has exactly one bit pattern, so number encoding is trivially injective and platform-independent (big-endian is forced regardless of host endianness).

### 5.4 Strings

Length-prefixed UTF-16 code units: 4-byte big-endian count of code units (`str.length`), then each `str.charCodeAt(i)` as 2 bytes big-endian. Properties:

- Lossless for every JS string, including lone surrogates — `"\uD800"` encodes as `0xD800` and nothing else, so class 3 cannot occur.
- No encode/decode round-trip exists anywhere in the design (the encoding is one-way; verification compares digests, never decodes), so class 4 cannot occur.
- The length prefix makes string encodings prefix-free against sibling content; combined with the leading tag this delimits every node unambiguously.
- Count overflow (`str.length > 0xFFFFFFFF`) is a hard error; unreachable in practice under `MAX_JSON_BYTES` and the property caps, but checked anyway (R4: fail closed, never truncate).
- **Aggregate string-size cap (R3): `MAX_ENCODED_STRING_UNITS = 1048576`.** The walk maintains a running total of code units encoded across every string in the tree (keys and values). Once the running total would exceed the cap, encoding fails closed immediately, before the oversized string's bytes are appended to the payload. This is a distinct cap from `MAX_BOARD_PROPERTIES`/`MAX_BOARD_NODES`, which bound the number of nodes, not the length of any one string: an in-process caller (not gated by `MAX_JSON_BYTES`, which applies only to CLI-parsed JSON text) can otherwise place one arbitrarily large string under an ignored field and force an unbounded code-unit walk and a payload allocation roughly twice its size. **Scope: the complete board, before projection.** Per 5.1's check ordering, this cap is enforced during the R4 canonical-domain pass over the complete board — the same pass that must already walk every string to check for non-finite numbers and other R4 violations — so a large string hidden inside a to-be-dropped volatile field (e.g. `evidence`) counts toward the total and cannot bypass the cap simply because projection will later discard it.

### 5.5 Objects and key ordering

- Keys come from `Object.keys` on the gated object (the plain-data gate has already rejected symbol keys, accessors, exotic prototypes, and Proxies). An own key named `"__proto__"` is, at this point, just a string own property (`JSON.parse` creates it as one) and is encoded like any other key — the encoder never assigns properties or builds literals, so class 1 has no mechanism.
- **Non-enumerable own properties (R3b), non-array objects only.** `Object.keys` returns only *enumerable* own string keys, but a non-enumerable own data property is still a real property a caller could set (e.g. `Object.defineProperty(card, 'note', { value: 'x', enumerable: false })`) and is invisible to this step. If `isDeeplyPlainData` accepted such an object (it inspects via `Reflect.ownKeys`/property descriptors, which do see non-enumerable properties), the encoder would silently omit that field from the digest, breaking the "every unknown field is covered" guarantee. The gate must therefore reject any **non-array** object carrying a non-enumerable own property — comparing `Object.keys(obj).length` against `Object.getOwnPropertyNames(obj).length` (after excluding symbol keys, already rejected) is sufficient to detect one. Arrays are exempted here (R3b) because their own `length` is always non-enumerable by spec; arrays are instead fully covered by R3a's exact-index check (5.2), which is more precise than this rule for the array case. Rejection, not enumeration-widening, keeps `Object.keys` as the single source of truth for both gate and encoder (for non-array objects; arrays never use `Object.keys` for their elements — 5.2 covers them by index).
- Each key is encoded as a `0x04` string node; entries are sorted by **bytewise lexicographic comparison of the encoded key bytes** (`Buffer.compare` on tag+length+payload). Because own string keys are unique, this order is total and deterministic; because the encoding is length-prefixed, the comparison is well-defined with no locale, no ICU, no `localeCompare` (R2).
- The entry count prefix, plus per-node tags and length prefixes, means two objects with different key sets, different values, or different sizes encode to byte streams that differ at the first divergent node.

### 5.6 Framing and injectivity argument

Every node's encoding is self-delimiting: tag, then fixed-size or count-prefixed payload, children encoded recursively under the same rule. Injectivity by structural induction: (base) distinct primitives of the same type differ in payload bytes (numbers: distinct bit patterns; strings: distinct code-unit sequences under equal-length comparison, or distinct length prefixes); distinct types differ at the tag byte. (step) Two composites of equal tag and count are equal iff all child encodings are pairwise equal, and self-delimitation means the byte stream decomposes into child encodings in exactly one way, so distinct child sequences produce distinct streams. Therefore the encoding is injective over the domain; SHA-256 carries that to the 32-byte digest under standard collision-resistance assumptions. The digest string is the 64-char lowercase hex of the SHA-256 (`node:crypto`, already imported by the module).

### 5.7 Bounds and failure behavior

The encoder walks with an explicit stack (mirroring `isDeeplyPlainData`), enforces the same `MAX_BOARD_NODES` / `MAX_BOARD_DEPTH` / `MAX_BOARD_PROPERTIES` caps as a defensive re-check, and returns an error result (never throws) on any domain violation. `validateBoard` computes the digest once, after the plain-data gate and before attestation checks, and treats encoder failure as a board validation error.

## 6. Attestation integration

**Flat fields, not a nested object.** `authenticatedControllerSnapshot` freezes a **shallow** spread and `isPlainDataAttestation` inspects only top-level descriptors; a nested `boardBinding: {...}` object would sit outside both protections. So the binding is two new top-level scalar fields on the existing attestation kinds:

- `boardBindingKind: "agency.board-binding.v1"` — versions the binding scheme (projection rule + encoding + hash) independently of the attestation kind.
- `boardDigest: <64 lowercase hex chars>` — the SHA-256 of the canonical declaration encoding per Section 5.

**Which attestations carry it:** `agency.pipeline-opt-in.v1` and `agency.card-evidence.v1`, both eventually **mandatory** — "eventually" because the rollout is phased (see the matrix below); neither kind's target state is optional. Role provenance already binds content hashes of the role itself and is board-independent: no change. Accounting: open question 3.

**Naming note — two unrelated fields share the name `schemaVersion`, distinguished below by full path.** `contracts.json`'s `attestations` object already has its own nested `schemaVersion` (currently `1`, pinned by `validateContracts`'s exact-object check against a hardcoded expected value in `agency-orchestration.js`) — call this **`contracts.attestations.schemaVersion`**, a policy field describing which shape of the *contracts document's* `attestations` block a given code version expects. Separately, every individual attestation *instance* (each opt-in, evidence, or role JSON object minted by a controller) carries its own top-level `schemaVersion` field, checked elsewhere in the validator (`snapshot.schemaVersion !== 1`) — call this **the attestation's own `schemaVersion`**, describing the shape of that one attestation kind. These are different fields on different objects that happen to share a name; nothing in this proposal changes the attestation's own `schemaVersion` — it stays `1`, because adding two new optional-then-mandatory top-level fields to an already-open, unenumerated-keys attestation object is backward compatible and does not change that kind's shape version.

**Rollout contract marker.** `contracts.json` gains `attestations.boardBindingRequired: boolean` alongside a bump of **`contracts.attestations.schemaVersion`** from `1` to `2` (requiring the code's hardcoded expected value in `validateContracts` to be updated in lockstep) and the new `boardBindingKind` constant. Neither the `contracts.attestations.schemaVersion` bump nor the `boardBindingKind` constant is phase-sensitive — both are one-time values fixed for the life of the scheme — so without the `boardBindingRequired` flag the warn-vs-reject policy would be decided solely by which validator code version is running, not by anything the contract declares, contradicting "the rollout is keyed off contracts." `boardBindingRequired` is `false` in release N (Phase 1) and flipped to `true` in release N+1 (Phase 2); `validateBoard`'s policy check (`validateContracts`) reads it, so a host can determine current enforcement policy from the contract alone.

**Disposition matrix.** Both predicates — `isPipelineOptInAttestation` and the evidence index inside `validateBoard` — apply the identical rule below to their respective attestation kind, keyed on `boardBindingRequired` and on what the attestation actually carries. **Precondition (R7): this matrix assumes the predicates can actually see a malformed field.** They read from `authenticatedControllerSnapshot`'s shallow spread, which silently drops any non-enumerable own property; without R7's fix to `isPlainDataAttestation` (reject non-enumerable own properties), a malformed field hidden behind a non-enumerable descriptor would appear identical to "absent" to everything below, which is exactly the miscategorization this matrix exists to prevent. Each of the two fields has exactly **three** possible states, not two: **absent** (the key is not present on the attestation at all — including, per R7, not present in an enumerable, snapshot-visible form); **malformed** (the key is present but is not a value of the correct type/format — not a string for `boardBindingKind`, or not exactly 64 lowercase hex chars for `boardDigest`); **well-formed** (present, correct type/format). The table below folds "malformed" into the same disposition as "well-formed-but-wrong" in every row, stated explicitly rather than left implicit: **a malformed value can never legitimately match anything it's compared against, so it is always treated identically to "well-formed but wrong/non-matching"** — for `boardBindingKind` that means malformed and wrong-value both fall under "present, wrong kind"; for `boardDigest` that means malformed and non-matching-value both fall under "present, does not match". Neither field's malformed state is ever conflated with "absent" — only a key that is truly missing from the attestation object (or, absent R7, hidden non-enumerably) counts as absent.

| `boardBindingKind` | `boardDigest` | `boardBindingRequired: false` (Phase 1) | `boardBindingRequired: true` (Phase 2) |
|---|---|---|---|
| absent | absent | **Warn** naming F6; attestation otherwise accepted (opt-in valid / evidence indexed) | **Reject** — attestation is not accepted |
| absent | present (well-formed or malformed) | **Reject** — partial binding is never valid, in either phase (an unversioned digest cannot be verified against a scheme) | **Reject** |
| present, correct kind | absent | **Reject** — same partial-binding rule | **Reject** |
| present, wrong kind (malformed or a value other than `"agency.board-binding.v1"`) | any (absent, malformed, well-formed-matching, or well-formed-non-matching) | **Reject** — a present-but-wrong `boardBindingKind` is wrong, not absent, so the absence-only warning never applies, regardless of what `boardDigest` holds | **Reject** |
| present, correct kind | present, well-formed, matches computed digest | **Accept** | **Accept** |
| present, correct kind | present, malformed or well-formed-but-does-not-match | **Reject** — a present-but-wrong digest always rejects, in either phase, whether the defect is a wrong value or a malformed format | **Reject** |

Both predicates read this table identically: only the fully-absent row differs by phase, and every other row rejects in both phases regardless of whether the defect is malformed-format or well-formed-but-wrong. This resolves the apparent conflict between Section 6's predicate description and the backward-compatibility phasing: the predicates as stated (require kind + matching digest) are the Phase 2 / `boardBindingRequired: true` column; Phase 1 carves out exactly one additional accepted case (both fields fully absent), nothing more permissive than that.

**Where warnings surface:** `validateBoard`'s existing warnings array (already used elsewhere in the validator), one entry per attestation instance found fully absent under Phase 1, naming the attestation kind, `pipelineId`/`cardId` as applicable, and issue #5 (F6). Warnings never suppress the board's other validation results and never appear when `boardBindingRequired: true`.

The evidence-index predicate applies the same binding-kind check as the opt-in predicate (both rows above), so evidence with a correct digest but a missing or wrong binding kind is never indexed — checking the digest alone would accept a malformed or future-scheme attestation on a coincidentally matching digest value. The index key stays `(pipelineId, cardId, evidenceId)`; the binding checks are filters at index-build time, so the O(1) lookup structure and the one-verification-per-attestation DoS fix are untouched.

A hard cut straight to Phase 2 (skip the warn phase) is defensible given the only known minter is the test suite's verifier (the CLI mints nothing) — owner's call, open question 1. Either way **the attestation's own `schemaVersion`** stays `1` throughout (per the naming note above, it identifies the attestation kind's own shape, not the binding scheme or rollout phase — those are `contracts.attestations.schemaVersion` and `boardBindingRequired`, both contract-level fields on a different object entirely), and the phase flip is keyed off `boardBindingRequired`, so old attestations fail according to the matrix above rather than ambiguously.

## 7. Verification plan

1. **Historical-collision regression vectors** — one dedicated test pair per class, each proving distinct inputs yield distinct digests (or rejection where R4 mandates it):
   - Class 1: a board with an own `"__proto__"` key (built via `JSON.parse`) vs the same board without it, and vs the same board with a different `"__proto__"` value ⇒ three distinct digests.
   - Class 2: a board containing `Infinity` (and variants with `-Infinity`, `NaN`) ⇒ digest computation **rejects**; the same position holding literal `null` ⇒ digests fine. No collision because the non-finite side never gets a digest.
   - Class 3: `"\uD800"` vs `"�"`, and `"\uD800"` vs `"\uDC00"` ⇒ distinct digests, all accepted.
   - Class 4: structural — assert the digest path contains no decode step; vector: a string whose UTF-8 round-trip is lossy still digests distinctly from its round-tripped form.
   - Plus: `-0` vs `0` ⇒ distinct digests; `0x05`[…] vs `0x06`{…} with colliding flattened content ⇒ distinct; nested-boundary ambiguity probes (e.g. `{"a":{"b":1},"c":2}` vs `{"a":{"b":1,"c":2}}`) ⇒ distinct.
   - Prototype quotient (R1): a board with an `Object.create(null)` object node vs the same board with the equivalent `Object.prototype` object at the same position, identical keys/values ⇒ **equal** digests (intentional quotient, not a collision) — and the fuzz oracle used to check this (below) must itself agree the two are "equal" under R1's content-only definition, not under a strict deep-equal that would call them different.
   - R3a: an array with an extra own property outside its dense indices/`length` (e.g. `cards.approval = "x"`) ⇒ rejected by the plain-data gate, not silently digested. Also: an array with an inherited (prototype-chain) numeric property filling what would otherwise be a hole, paired with an unrelated extra own property that keeps the `Reflect.ownKeys` count coincidentally matching `length + 1` ⇒ still rejected (proves the check is exact-index, not cardinality-only).
   - R3b: a **non-array** object with a non-enumerable own property (`Object.defineProperty(..., { enumerable: false })`) ⇒ rejected by the plain-data gate. A plain array (whose own `length` is always non-enumerable) with no other defect ⇒ still accepted, proving the array exemption doesn't regress into rejecting every array.
   - R3c: a card whose `stopCondition` is deleted as an own property while `Object.prototype.stopCondition` supplies one ⇒ rejected by the plain-data gate under *both* inherited values, proving the two different effective declarations can no longer share a digest; likewise for an inherited `budget` value. An otherwise clean board also fails closed while `Object.prototype` carries any enumerable property (pollution is process-global, so no board's digest is trustworthy while it lasts) and digests identically again once the pollution is removed. A null-prototype tree is unaffected ⇒ proving the rule rejects actual exposure, not the mere existence of pollution.
   - R3 (string cap): a single string field exceeding `MAX_ENCODED_STRING_UNITS` (1,048,576 code units) ⇒ digest computation fails closed before payload allocation; a board just under the cap still digests; the same oversized string placed inside a volatile field (e.g. `evidence` on a non-`done` card) still fails closed, proving the cap is enforced pre-projection over the complete board, not only on the surviving projected value.
   - schemaVersion naming: a contract with `contracts.attestations.schemaVersion: 2` and the new keys, verified against an attestation instance whose own `schemaVersion` field is still `1` ⇒ accepted (proves the two fields are independently checked and neither regresses the other).
   - Evidence binding-kind: an authenticated evidence snapshot with a correct `boardDigest` but a missing or wrong `boardBindingKind` ⇒ not indexed, same as a digest mismatch.
   - Disposition matrix (Section 6): one test per row, for both attestation kinds, under both `boardBindingRequired` values — six rows × two kinds × two phases = 24 cases minimum, covering fully-absent (warn under Phase 1, reject under Phase 2), each partial combination (always reject), and present-correct vs present-wrong (accept / reject in both phases). Plus, at least one dedicated malformed-format case per field (a non-string `boardBindingKind`; a `boardDigest` of the wrong length or containing uppercase/non-hex characters) ⇒ rejects identically to the corresponding well-formed-but-wrong case, proving malformed and wrong-value are not accidentally treated differently.
   - R7: an attestation with `boardBindingKind` (or `boardDigest`) defined via `Object.defineProperty(attestation, name, { value: 'wrong-or-malformed', enumerable: false })` ⇒ rejected by `isPlainDataAttestation` outright (not accepted and then silently dropped by the snapshot spread), proving a non-enumerable malformed field cannot slip through as "absent" and warn-accept under Phase 1.
2. **Property-based fuzzing.** A generator over the accepted domain (post-gate JSON-shaped plain data: finite doubles including `-0`, strings including lone surrogates, both `Object.prototype` and null-prototype object variants, nesting within caps). N random pairs (N ≥ 10k in CI-feasible time): assert `digest(a) === digest(b)` **iff `Project(a)` and `Project(b)` are equal under R1's content-only equality** (SameValue on leaves, ignoring volatile-field values and ignoring object-prototype identity — not a strict deep-equal like `assert.deepStrictEqual`, which checks both and would misreport R1's intentional quotients as collisions). The mutation harness applies one random structural mutation to a random accepted board and classifies the mutation before asserting: a mutation whose *only* effect is changing a volatile field's value (`board.enabled`, `board.correctionCycles`, or a card's `status`/`attempts`/`evidence`) and/or an object node's prototype (`Object.prototype` ↔ null) must leave the digest **unchanged** (both are R1's quotients); a mutation that changes any non-volatile field's key or value content must leave the digest **changed**. A mutation harness that asserts "the digest always changes" for every mutation, with no such classification, would itself fail against a correct implementation.
3. **Cross-version determinism.** Golden digest vectors (fixed boards → fixed hex digests) committed to the test suite and run on two Node majors in CI (current LTS pair); any byte-level drift fails loudly.
4. **Existing suite stays green.** All 57 tests in `tests/agency-orchestration.test.js` pass unchanged in phase 1 except tests that mint opt-in/evidence attestations, which are extended to carry the two new fields; the plain-data gate, evidence-index behavior, and error vocabulary are otherwise untouched.

## 8. Explicit non-goals

- No dispatcher, no worker supervision, no live enforcement — `validateBoard` remains validation-only, per the README.
- No change to the frozen exported-API trust boundary: trusted in-process caller, plain JSON-derived data, `agency-doctor` CLI as the only supported entrypoint. The digest hardens what an authenticated controller approves; it does not turn the validator into a sandbox.
- No attestation minting in the CLI, and no controller verifier implementation — an enabled board still intentionally rejects without a trusted host controller.
- No canonical-JSON interop goal: the byte format exists solely to be hashed, not exchanged.

## 9. Owner decisions (resolved 2026-08-28)

All four open questions were put to the owner and answered; the defaults stated in earlier drafts were each confirmed. These are now decisions of record for the implementation:

1. **Rollout: two-phase.** Release N (`boardBindingRequired: false`): fully-absent binding warns naming F6, any partial or wrong binding still rejects. Release N+1 (`boardBindingRequired: true`): fully-absent binding also rejects. Full disposition matrix in Section 6.
2. **Projection scope: denylist projection as specified in 5.1.** Volatile denylist confirmed: `enabled`, `correctionCycles`; per card `status`, `attempts`, `evidence`. Any unlisted field is covered by the digest.
3. **Accounting: not bound.** `agency.accounting.v1` stays as-is; revisit if cost enforcement ever leaves advisory mode.
4. **Contracts surface: yes, additive keys.** `contracts.json` gains `attestations.boardBindingKind` alongside a bump of `contracts.attestations.schemaVersion` (the contracts-document policy field, not the unrelated same-named field carried by each attestation instance — see Section 6's naming note) from 1 to 2, plus `attestations.boardBindingRequired` (`false` in release N, `true` in release N+1) so the warn-vs-reject rollout phase is itself a pinned contract value rather than an artifact of validator code version (see Section 6).
